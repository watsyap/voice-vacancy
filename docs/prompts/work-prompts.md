# Рабочие промты (A0–A7)

Промты, которыми ИИ помогал делать задание: анализ, спецификация, код, QA, тексты.
Продуктовые промты, которые работают внутри приложения, — в `b1-analyze.md` и `b2-generate.md`.
Первые версии Б1/Б2 (со `score` 0–100) отброшены после анализа A1 (`docs/analysis.md` §5).

---

## А0. Контекст (вставлялся в начало каждого рабочего промта)

```
Продукт: сервис автоматического найма. Фича: бизнес-заказчик (нанимающий менеджер)
голосом отвечает на 4 вопроса о будущем сотруднике, система распознаёт речь,
проверяет смысловую полноту ответа и генерирует структурированное описание вакансии.

Вопросы (переформулированы: исходные звучали про уже работающего человека, а не про вакансию):
1. Какие две-три задачи ежедневно выполняет сотрудник в этой роли?
2. Над каким проектом сотрудник будет работать первые 6 месяцев?
3. Что дальше: после этих полугода он продолжит этот проект или перейдёт на другой? Какой именно и с чем он будет связан?
4. Какими особыми инструментами, программами и знаниями должен владеть сотрудник, чтобы эффективно выполнять работу?

Ключевые решения (не пересматривать без причины):
- Кольцо прогресса (референс Face ID) из 4 сегментов = 4 вопроса.
  Во время речи штрихи кольца реагируют на громкость (живая обратная связь «слышу»).
  Сегмент заполняется по СМЫСЛОВОЙ полноте ответа (0–100), а не по времени речи.
- Если ответ неполный — максимум ОДИН уточняющий голосовой вопрос, затем идём дальше.
- Сложность скрыта: пользователь видит «Слушаю → Понял → Следующий вопрос», без JSON/скоров.
- Финал: экран вакансии с возможностью поправить текст и скопировать.
- Стек: React + Vite + TypeScript, распознавание — Web Speech API (ru-RU),
  LLM через serverless-функцию (Vercel). Фолбэк: текстовый ввод, если голос недоступен.
- Демо-режим без ключа API: детерминированные ответы, чтобы проверяющий мог всё прокликать.

Критерии оценки: понимание задачи, спецификация без вопросов, работающий прототип,
прозрачная работа с ИИ, защищаемость решений. Минимализм: каждый элемент обоснован.
```

Часть этих решений пересмотрена в A1 (скор от модели, «Понял» без содержания, Q3, демо-режим) — см. `docs/analysis.md` §5.

## А1. Анализ задачи и допущения → `docs/analysis.md`

```
[А0]
Ты — senior продуктовый дизайнер и жёсткий критик. Разбери задание:
1. Цель бизнеса и как её измерить.
2. Пользователь, контекст использования (где, с какого устройства, сколько времени готов потратить).
3. Задача пользователя в одном предложении (JTBD).
4. Ограничения (технические: браузеры и Web Speech API, разрешения микрофона; продуктовые).
5. Неоднозначности формулировки задания → для каждой: допущение + почему оно разумно.
6. Риски: где пользователь бросит сценарий.
Не придумывай фичи. Формат: короткие списки, без воды. В конце — 3 главных решения, которые
сильнее всего влияют на оценку.
```

## А2. User flow и состояния → `docs/flow.md`

```
[А0]
Построй user flow: вход → разрешение микрофона → вопрос 1..4 (запись, анализ, уточнение)
→ генерация → просмотр/правка → копирование.
Затем таблица состояний: состояние | триггер | что видит | что может сделать | как выйти.
Обязательно: первый вход, микрофон запрещён, микрофона нет, браузер не поддерживает,
тишина >5 c, слишком короткий ответ, шум/пустое распознавание, анализ идёт, анализ упал,
неполный ответ (уточнение), повтор ответа, пропуск вопроса, отмена посреди записи,
генерация долгая (>10 c), генерация упала, частичный результат, оффлайн, вкладка скрыта
во время записи, перезагрузка страницы (что сохраняется).
Для каждого — без новых попапов, если можно обойтись состоянием кольца/подписи.
```

## А3. Спецификация → `docs/spec.md`

```
[А0] [вставь результат А1 и А2]
Напиши спецификацию по шаблону:
- Проблема и задача пользователя (1–3 предложения)
- Сценарии и user flow
- Экраны/компоненты: назначение КАЖДОГО элемента (если назначение не формулируется — удали элемент)
- Состояния (таблица из А2, доработанная)
- Критерии приёмки: Дано/Когда/Тогда, проверяемые, с числами (тайминги, пороги)
- Анимация кольца: состояния, длительности, easing, prefers-reduced-motion
- Чего делать нельзя
- Что вырезано и почему
- Метрики успеха
- Открытые вопросы и допущения
Требование: разработчик или ИИ-агент реализует по документу без единого вопроса.
Пиши сжато; таблицы вместо прозы где возможно.
```

## А4. Документация для агентной разработки → `AGENTS.md`

```
[А0] [вставь спецификацию из А3]
Сгенерируй AGENTS.md для репозитория: стек, структура папок, команды (dev/build/test),
токены дизайна (цвет, типографика, отступы, радиусы, длительности анимаций) как CSS-переменные,
список компонентов с props и состояниями, контракт API serverless-функций (request/response JSON,
коды ошибок), правила: что агенту нельзя менять без спеки, definition of done
(все состояния из таблицы реализованы, критерии приёмки проходят, работает без ключа API в демо-режиме).
```
Уточнения при запуске: не дублировать спеку (только ссылки), одна машина состояний на `useReducer` с ID S1–S24,
обязательные тесты (полнота, демо-эвристики, редьюсер S9–S12), стоп при противоречии, ≤ 250 строк.

## А5. Реализация (Claude Code)

```
Прочитай AGENTS.md и docs/spec.md. Реализуй по этапам, после каждого — коммит и проверка
критериев приёмки этого этапа:
1. Каркас, токены, экран вопроса, компонент ProgressRing (4 сегмента, реакция на громкость).
2. Голос: Web Speech API ru-RU, промежуточный текст, тишина, ошибки разрешений, текстовый фолбэк.
3. Serverless /api/analyze (продуктовый промт Б1) + демо-режим. Заполнение сегмента по полноте слотов.
4. Уточняющий вопрос (Б1 followup), лимит 1.
5. /api/generate (Б2) + экран вакансии: правка, копирование.
6. Все состояния из таблицы спеки; оффлайн; восстановление после перезагрузки (localStorage).
7. Деплой на Vercel.
Не добавляй ничего, чего нет в спеке. Если спека противоречива — остановись и опиши противоречие.
```
